Module 05

코드 리뷰와 자동 반영

Code Review and Comment Resolution

리뷰 3층 비교Writer/Reviewer 2세션REVIEW.mdfork → PR → 자동 코멘트코멘트 자동 반영

이 모듈에서

리뷰는 세션을 갈라서, 반영은 손을 떼고

이 모듈에서는 리뷰 세션을 분리하고 PR에 자동 리뷰를 붙여 코멘트까지 반영시킵니다.

이 모듈에서 배울 것

  • 구현 세션과 리뷰 세션을 갈라, 신선한 컨텍스트가 diff만 읽고 결함을 다시 찾게 합니다.
  • 로컬 명령·오픈소스 Actions·관리형 앱을 플랜과 비용으로 가르고, 되는 두 층을 PR에 붙입니다.
  • REVIEW.md로 Important와 Nit을 가르고, 브랜치를 손대지 않은 채 코멘트를 반영해 체크를 통과시킵니다.
왜 이걸 하나

같은 세션은 방금 쓴 코드의 결정을 의심하지 않고, 기준이 사람마다 다르면 코멘트도 갈립니다.

왜 이걸 하나

방금 쓴 코드는 쓴 세션이 못 본다

구현 이력이 남은 세션은 자기 결정을 의심하지 않습니다.

01

편향

자기가 고른 방식이 옳다는 전제로 diff를 읽습니다.

02

이력이 가린다

대화가 길수록 변경 자체보다 그때의 사정이 먼저 보입니다.

03

기준이 사람마다

Important의 정의가 없으면 코멘트가 사람마다 갈립니다.

신선한 컨텍스트는 코드 리뷰를 개선한다. Claude가 방금 자기가 쓴 코드에 편향되지 않기 때문이다.

Anthropic · Claude Code Best Practices (code.claude.com/docs/en/best-practices)

경계 문장

Nit은 로컬에서 끝내고, Important만 올린다

비교표가 정책이 되려면 어느 층이 무엇을 맡는지 한 줄로 고정해야 합니다.

로컬 층 · 푸시 전

Nit은 여기서 끝낸다

  • 이름·주석·서식은 리뷰 세션에서 정리하고 푸시합니다.
  • 토큰은 내 세션에서만 씁니다.

Actions 층 · PR

Important 후보만 올린다

  • 정확성·요구사항에 걸리는 것만 코멘트로 남깁니다.
  • 코멘트는 팀 기록이 되어 지표의 분모가 됩니다.

📌메모 — 관리형 Code Review는 Team/Enterprise 전용에 리뷰당 평균 $15~25라, 이 모듈에서는 실행하지 않고 비교로만 둡니다.

산출물 미리보기

REVIEW.md — 경계를 파일로 고정한다

리뷰 세션과 Actions가 같은 파일을 읽으니 두 층의 기준이 어긋나지 않습니다.

REVIEW.md docs/templates/
IMPORTANT — 머지를 막는다
정확성 잘못된 값 · 잘린 행 · 경합 / 요구사항 SPEC.md 항목 누락 · 범위 밖 변경

이름 · 주석 · 서식. 로컬 층에서 끝낸다
완료 정의
Important 0건 · 체크 green · Nit은 반영하거나 이유를 적는다

강사 화면 ①

두 세션이 같은 diff를 다르게 본다

왼쪽은 구현 브랜치를 가진 세션, 오른쪽은 새 터미널에서 새로 연 리뷰 세션입니다.

assets/images/05-07-writer-reviewer.png 두 터미널을 나란히 — 왼쪽 구현 세션의 프롬프트 A 응답, 오른쪽 새 리뷰 세션의 프롬프트 B 응답

⚠️확인 — 오른쪽 첫 응답에 Important와 Nit이 나뉘어 있으면 REVIEW.md가 읽힌 것입니다.

강사 화면 ②

PR을 열면 코멘트가 먼저 와 있다

pull_request opened로 Actions가 돌고, 코멘트 하나에 Important와 Nit이 담겨 옵니다.

assets/images/05-08-pr-auto-comment.png fork에서 PR을 연 직후 Conversation 탭 — claude 봇의 Important 1건·Nit 2건 코멘트가 보이는 화면 전체

📌메모 — PR을 연 시각과 코멘트가 도착한 시각을 워크시트에 적습니다. 그 차이가 지표 ①입니다.

즉시 따라하기 1/7

레포를 fork한다

왜 이걸 하나

Actions는 fork 안에서 돌고, 그 안의 Claude는 본인 구독으로 인증됩니다. 강사 레포에는 아무것도 올리지 않습니다.

  1. 03
    Fork → 본인 계정 → Create fork 강사 레포 페이지 오른쪽 위의 Fork를 누릅니다. 기존 폴더에서는 git remote set-url origin 뒤에 fork 주소를 붙여 원격을 바꿉니다.
    fork의 Actions 탭이 비활성이면 "I understand my workflows, go ahead and enable them"을 먼저 눌러야 돕니다.

즉시 따라하기 2/7

토큰을 받는다

왜 이걸 하나

이 토큰이 fork 안의 Actions와 본인 구독을 잇는 유일한 연결입니다.

  1. 04
    claude setup-token 터미널에서 claude setup-token → 브라우저 승인 → 터미널에 찍힌 토큰을 복사합니다. 이 값은 채팅이나 파일에 남기지 않습니다.
    토큰은 Secret 한 곳에만 들어갑니다. 터미널 창을 닫기 전에 복사합니다.

즉시 따라하기 3/7

Secret에 넣는다

왜 이걸 하나

Secret 이름이 워크플로 YAML의 이름과 한 글자라도 다르면 Actions가 조용히 실패합니다.

  1. 05
    New repository secret fork의 Settings → Secrets and variables → Actions → New repository secret. 이름은 CLAUDE_CODE_OAUTH_TOKEN, 값은 방금 복사한 토큰입니다.
    이름은 복사해서 붙입니다. 손으로 치면 한 글자가 어긋납니다.

화면 ① · Secret

Secret 이름은 이 값 그대로

fork의 Settings 안입니다. 빨간 상자 두 곳만 채우고 Add secret을 누릅니다.

assets/images/05-15-actions-secret.png fork의 Settings → Secrets and variables → Actions → New repository secret 화면, 이름 칸에 CLAUDE_CODE_OAUTH_TOKEN을 친 상태

즉시 따라하기 4/7

푸시하고 PR을 연다

왜 이걸 하나

base가 강사 레포를 가리키면 PR이 남의 레포로 가고 Actions도 거기서 돕니다.

  1. 06
    푸시 → Compare & pull request → Create git push -u origin 뒤에 브랜치 이름을 붙여 푸시합니다. GitHub의 Compare & pull request → base를 본인 fork의 main으로 → 본문에 프롬프트 A의 결과 → Create pull request.
    Create를 누르는 순간 Actions가 돕니다. PR을 연 시각을 워크시트에 적습니다.

화면 ② · PR

base는 내 fork, compare는 내 브랜치

Compare & pull request를 누른 뒤 화면입니다. base repository가 본인 계정인지 먼저 봅니다.

assets/images/05-17-create-pr.png Compare & pull request 직후 화면 — base repository가 본인 fork, compare가 본인 브랜치인 상태 전체

즉시 따라하기 5/7

PR이 도는 동안 리뷰 세션을 엽니다

왜 이걸 하나

리뷰 세션에 구현 이력이 없어야 그때의 사정이 아니라 diff 자체가 읽힙니다.

  1. 01
    구현 브랜치를 정한다 3교시 브랜치가 있으면 그대로, 없으면 git checkout review-fixture. 그 세션에서 다음 장의 프롬프트 A를 넣습니다.
  2. 02
    새 터미널에서 리뷰 세션을 연다 새 탭에서 claude를 새로 실행하고 /model로 상위 모델을 고른 뒤 프롬프트 B를 넣습니다. 상위 모델은 리뷰 세션에서만 씁니다.
    프롬프트 B의 결과에 Important가 없으면 리뷰가 아니라 요약을 한 것입니다. 에러 갤러리 ②로 갑니다.

프롬프트 A · 구현 세션

리뷰어가 볼 곳을 먼저 짚는다

결과는 PR 본문에 그대로 붙입니다. 파일을 만들지 않으니 diff가 늘지 않습니다.

프롬프트 A · 구현 브랜치 세션에서 입력 
git diff main..HEAD 를 읽고 이 변경이 무엇을 바꿨는지 세 줄로 요약해라.
리뷰어가 먼저 봐야 할 파일:줄을 3곳 지목하고 이유를 한 줄씩 붙여라.
결과는 화면에만 내라. 파일을 만들거나 코드를 고치지 마라.
의미

구현 세션의 맥락을 PR 본문 한 장으로 꺼내 리뷰어의 진입점을 만듭니다.

본인 업무

PR을 열기 전에 설명을 쓰던 일이 이 프롬프트로 바뀝니다.

바꿔 끼우는 자리

비교 범위. 예: main..HEAD 대신 release/1.2..HEAD, 지목 개수 3곳

프롬프트 B · 리뷰 세션

diff와 REVIEW.md만 읽게 한다

새 세션이라 이전 대화가 없고, 읽을 범위를 둘로 좁혀 편향을 막습니다.

프롬프트 B · 새 터미널의 리뷰 세션에서 입력 
git diff main..HEAD 와 docs/templates/REVIEW.md 만 읽어라. 다른 파일은 열지 마라.
지적을 Important 와 Nit 두 묶음으로 나눠라.
정확성이나 요구사항에 영향을 주는 것만 Important 로 올리고, 각 항목에 파일:줄과 한 줄 근거를 붙여라.
코드는 고치지 마라.
의미

신선한 컨텍스트에 REVIEW.md의 경계를 주고 diff만 판정하게 합니다.

본인 업무

동료 PR을 열어 보기 전에 먼저 돌리는 1차 리뷰가 됩니다.

바꿔 끼우는 자리

기준 파일 경로. 예: 팀 REVIEW.md, 화면 계층용 REVIEW-ui.md

💡팁 — /code-review 한 줄로도 리뷰가 돌지만 그 명령은 REVIEW.md 를 읽지 않습니다. 폴백 장에서 그 차이를 씁니다.

즉시 따라하기 6/7

코멘트를 확인한다

왜 이걸 하나

Important에 결함 ④가 잡혀 있어야 다음 단계에서 반영시킬 대상이 있습니다.

  1. 07
    Actions 탭 → Conversation 탭 Claude Review가 끝나면 Conversation에 코멘트가 옵니다. Important에 결함 ④(정렬 헤더 뒤 마지막 행 잘림)가 있는지, 나머지가 Nit인지 봅니다.
    코멘트가 도착한 시각을 적습니다. PR을 연 시각과의 차이가 지표 ①입니다.

즉시 따라하기 7/7

반영은 맡긴다

왜 이걸 하나

사람이 브랜치를 건드리지 않고 해결된 코멘트가 4주 뒤 지표 ④의 분자입니다. 여기서 첫 건을 만듭니다.

  1. 08
    PR 코멘트 칸에 프롬프트 C 다음 장의 프롬프트 C를 PR 코멘트 칸에 그대로 씁니다. 로컬 브랜치는 건드리지 않습니다. 커밋과 푸시는 Actions 안의 Claude가 합니다.
    반영 커밋의 작성자가 claude[bot]이면 통과입니다. 내 이름이면 손을 댄 것입니다.

프롬프트 C · PR 코멘트

멘션 한 줄로 PR을 green으로

터미널이 아니라 PR의 코멘트 칸에 씁니다. 멘션이 Actions를 다시 깨웁니다.

프롬프트 C · PR Conversation 코멘트 칸에 입력 
@claude 코멘트 반영해 PR을 green으로
의미

열린 코멘트를 전부 처리하고 체크가 통과할 때까지 커밋을 밀게 합니다.

본인 업무

리뷰 코멘트를 하나씩 손으로 고치던 왕복이 멘션 한 줄로 줄어듭니다.

바꿔 끼우는 자리

뒤에 붙이는 범위 문구. 예: "Important만 반영해" · "Nit은 이유만 남겨"

⚠️확인 — 워크플로에 issue_comment 트리거가 없으면 멘션이 반응하지 않습니다. 에러 갤러리 ③입니다.

강사 화면 ③

체크가 green으로 바뀐 화면

claude 봇의 커밋이 올라오고 체크가 통과로 바뀌면 이 모듈의 통과선입니다.

assets/images/05-21-pr-green.png 프롬프트 C 코멘트 아래로 claude 봇의 응답과 반영 커밋, 하단의 All checks have passed가 보이는 Conversation 화면

⚠️검증 포인트 — 반영 커밋의 작성자가 claude[bot]이고 로컬 git log에는 아직 없어야 합니다. git pull로 받아 옵니다.

폴백

토큰이 막히면 로컬 리뷰를 코멘트로 올린다

setup-token이나 Secret에서 막힌 사람은 이 경로로 갑니다. 통과 증거로 인정합니다.

01

리뷰 출력을 복사한다

프롬프트 B의 결과나 /code-review 출력에서 Important와 Nit 부분을 그대로 복사합니다.

02

PR 코멘트로 붙인다

PR의 Conversation 코멘트 칸에 붙여 넣고 Comment를 누릅니다. 첫 줄에 "로컬 리뷰"라고 적습니다.

03

반영은 구현 세션에

구현 세션에 "Important만 고치고 npm test를 통과시켜라"를 넣고 푸시합니다. 작성자가 나인 것은 폴백이라 허용합니다.

자체 실습

네 것으로 바꿔 한 번 더

본인 3교시 브랜치로 같은 루프를 처음부터 돌립니다.

01

리뷰 세션

/clear 뒤 새 터미널에서 프롬프트 B로 Important와 Nit을 가릅니다.

02

PR과 자동 코멘트

푸시 → PR → 코멘트. PR을 연 시각과 도착 시각을 적습니다.

03

멘션으로 반영

프롬프트 C → claude[bot] 커밋 → 체크 green. 지표 ② O·X도 적습니다.

⚠️도달 기준 — 본인 PR에 자동 코멘트가 달리고, 결함 ④가 Important, 나머지가 Nit으로 갈린 뒤, 브랜치를 직접 편집하지 않고 체크가 통과로 바뀐 화면을 보입니다.

막히면

여기서 자주 걸린다

셋 중 하나입니다. 메시지도 Actions 로그의 빨간 줄도 그대로 Claude에 붙여넣습니다.

01

Actions가 돌지 않는다

fork의 Actions 탭이 꺼져 있거나 Secret 이름이 다릅니다. 탭에서 enable, 이름은 YAML과 대조합니다.

02

Important가 0건이다

REVIEW.md를 못 읽은 것입니다. 레포 루트에 복사하거나 프롬프트에 경로를 적습니다.

03

@claude가 반응이 없다

워크플로에 issue_comment 트리거가 빠진 것입니다. 배포된 YAML과 대조하고, 안 되면 폴백으로.
