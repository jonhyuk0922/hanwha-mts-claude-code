Module 02

검증 우선 프롬프팅

Verification-First Prompting

검증 위계 3층게이트 4단실패 테스트 선행스크린샷 비교증거 4칸

이 모듈에서

체크를 첫 프롬프트에 넣는다

고쳤는지 확인하는 일을 사람 대신 Claude가 스스로 하게 만듭니다.

이 모듈에서 배울 것

  • 테스트와 빌드처럼 Claude가 직접 돌릴 수 있는 체크를 첫 프롬프트에 함께 적어, 사람이 확인해 주는 왕복을 없앤다.
  • 결정론적 체크를 먼저, 화면 비교를 그다음에 두는 순서를 정하고, 게이트를 어디까지 세게 걸지 네 단계로 비교한다.
  • 로직 결함 두 건은 실패 테스트로 먼저 재현하고, 화면 결함 한 건은 스크린샷 비교로 잡은 뒤 실행 명령과 출력을 증거로 남긴다.

왜 이걸 하나

고쳐 달라고만 하면 왕복이 생긴다

확인을 사람이 맡는 순간, 고쳐졌는지 보는 일이 매번 우리 차례로 돌아옵니다.

검증 없는 요청

이메일 검증 함수를 구현해 줘

  • 맞는지는 사람이 열어 봐야 안다
  • 틀리면 다시 설명하고 다시 기다린다
→
검증을 넣은 요청

validateEmail을 쓰고, 이 테스트 케이스로 돌려 통과를 보여 줘

  • 통과와 실패를 Claude가 스스로 읽는다
  • 한 턴 안에서 고치고 끝난다

공식 Best Practices(code.claude.com/docs/en/best-practices)의 예시 쌍을 우리 말로 옮겼습니다.

근거

검증 수단이 결과 품질을 가른다

"Give Claude a way to verify its work. If Claude has that feedback loop, it will 2-3x the quality of the final result."

Boris Cherny (Claude Code 창시자) · X 스레드 2026년 1월 · tip 13
왜 이걸 하나

가이드 없는 시도는 약 33%만 성공합니다(Anthropic 자료, DataCamp 인용). 차이를 만드는 것은 설명의 길이가 아니라 Claude가 스스로 돌릴 수 있는 체크입니다.

검증 위계 3층

결정론적인 체크가 앞에 온다

린트와 테스트가 먼저, 화면 비교가 다음, 모델의 판단은 마지막입니다.

층무엇으로 판정하나우리 레포에서같은 입력이면
1 · rules스크립트가 통과·실패를 낸다npm test · npm run lint · npm run typecheck같은 답
2 · visual기준 화면과 지금 화면의 차이관심종목 캡처를 붙여넣어 비교기준이 있어야 같다
3 · judge모델이 결과를 읽고 판단한다리뷰 세션 (5교시)흔들릴 수 있다

앞 층이 못 잡는 것만 다음 층으로 넘긴다. 출처 — Thariq Shihipar(Claude Code 팀)의 검증 위계.

게이트 4단

검증을 어디까지 세게 거나

같은 체크라도 누가 언제 판정하느냐에 따라 강도가 네 단계로 갈립니다.

단어떻게 거나누가 판정하나이 교육에서
1 · 프롬프트 안 실행"고친 뒤 npm test를 돌려라"Claude 자신, 한 턴 안에서이 모듈
2 · /goal 조건완료 조건을 선언한다별도 평가자가 매 턴 재확인소개만
3 · Stop 훅통과 전까지 턴을 끝내지 못한다스크립트4교시 훅 체크인
4 · 검증 서브에이전트신선한 모델이 결과를 반박한다다른 세션5교시 리뷰 세션

이 모듈은 1단으로 시작하고, 4교시와 5교시에서 3단과 4단을 레포와 PR에 건다.

강사 화면

같은 결함, 두 가지 첫 프롬프트

결함 ②를 두 세션에서 따로 고치고, 끝난 뒤 두 세션의 상태를 나란히 봅니다.

  1. A
    "수량 검증이 이상해요, 고쳐 주세요"만 보낸다고쳤다는 답이 올 때마다 화면에서 확인하고 아직 안 된다고 알려 준다. 이 왕복이 쌓인다.
  2. B
    /clear 뒤, 실패 테스트 예시와 npm test 지시를 첫 프롬프트에 넣는다실패 출력을 Claude가 스스로 읽고 고친 뒤, 통과 출력까지 한 턴에 낸다.
assets/images/02-7-session-b.png 세션 B 터미널 / 첫 프롬프트 한 번에 테스트 작성 → 실패 출력 → 수정 → 통과까지 이어진 화면

검증이 곧 토큰 절감

왕복이 사라지면 사용률이 내려간다

사람이 답을 한 번 줄 때마다 지금까지의 대화 전체가 한 번 더 실립니다.

assets/images/02-8-context-a-b.png 두 세션 종료 시점의 /context 화면 / 왼쪽 A · 오른쪽 B / 사용률과 사람이 답한 왕복 수를 나란히
왜 이걸 하나

왕복 한 번은 한 줄 프롬프트가 아니라 대화 전체를 다시 읽는 비용입니다. 체크를 Claude 안으로 넣으면 그 왕복이 세션에서 통째로 빠집니다. 왕복 횟수는 이 뒤로도 태스크당 비용을 재는 단위로 계속 씁니다.

즉시 따라하기 (1/2)

결함 ② — 실패 테스트를 먼저 쓴다

main에서 npm test 통과를 보고 시작합니다.

  1. 01
    출발 확인git checkout main → npm test. 전부 통과한다. 결함 ②를 건드리는 테스트가 아직 없다.
  2. 02
    다음 장의 예시 프롬프트를 그대로 보낸다Claude가 tests/validateQty.boundary.test.ts를 쓰고 npm test 실패를 먼저 보여 준 뒤, 같은 턴에서 src/lib/validateQty.ts를 고쳐 통과까지 낸다.
assets/images/02-9-test-fail.png 참가자 터미널 / 프롬프트 전송 직후 npm test 실패 출력 / Expected: true · Received: false 두 줄이 보이는 상태
왜 이걸 하나

수정 전에 실패를 봐야, 그 테스트가 정말 결함을 잡는지 알 수 있습니다.

프롬프트

실패 테스트 선행 — 템플릿과 예시

왼쪽의 빈칸 세 자리를 채우면 어느 결함에도 같은 골격이 됩니다.

템플릿
[대상 파일]의 결함을 고치기 전에,
먼저 실패하는 테스트를 [테스트 파일]에 써라.
재현 조건: [입력 → 기대값]
npm test 를 실행해 그 테스트가 실패하는 출력을 보여 준 뒤에만 [대상 파일]을 고쳐라.
고친 뒤 npm test 를 다시 실행해 통과 출력을 보여라.
테스트의 기대값은 바꾸지 마라.

재현 조건: validateQty(100, 100) → true (잔여 수량과 같은 수량은 주문 가능)

⚠️검증 포인트 — 출력에 Expected: true Received: false 가 먼저 보이고, 그 뒤에 통과 출력이 와야 합니다.

즉시 따라하기 (2/2)

결함 ③ — 기준 화면과 비교한다

6행을 넘으면 종목명이 등락률 칸을 침범하는데, 눈으로는 놓치기 쉽습니다.

  1. 01
    기준 화면과 지금 화면을 캡처한다기준은 강사가 공유한 정상 화면. 지금 화면은 npm run dev로 띄우고 Ctrl+Cmd+Shift+4로 같은 영역을 클립보드에 담는다.
  2. 02
    붙여넣고 고정 프롬프트를 보낸다입력창에 Ctrl+V로 붙인다. Claude가 스스로 캡처하지 못해도 붙여넣은 두 장으로 비교한다. 고친 뒤 다시 캡처해 한 번 더 비교한다.

기준이 있어야 "이상하다"가 "어디가 다르다"로 바뀌고, 그 목록이 곧 수정 지시가 됩니다.

바꿔 끼우는 자리

붙여넣는 기준 스크린샷 — 시안 캡처, 이전 배포 캡처, 다른 해상도 캡처로 바꿉니다.

자체 실습 (1/2)

네 것으로 바꿔 한 번 더

/clear로 시작해 결함 ①을 같은 골격으로 잡습니다.

  1. 01
    템플릿의 세 자리를 결함 ①로 바꾼다대상 src/lib/applyQuote.ts · 테스트 tests/applyQuote.race.test.ts · 재현 조건 "앞선 타임스탬프의 응답이 늦게 와도 최신 호가 71300이 남는다"
  2. 02
    보내고 실패부터 확인한다출력에 Expected: 71300 Received: 71250 이 보인 뒤에만 수정으로 넘어가 통과까지 받는다.
왜 이걸 하나

세 곳만 바꿨음을 손으로 확인해야, 회사 레포의 버그 티켓에도 같은 골격이 갑니다.

자체 실습 (2/2)

결함 ③까지 마치고 증거를 남긴다

화면 결함을 비교 프롬프트로 잡고, 결함마다 네 칸을 채웁니다.

  1. 03
    화면 결함 ③을 비교 프롬프트로 잡는다차이 목록 → 수정 → 다시 캡처해 차이 없음까지 확인한다.
  2. 04
    결함 ①②③ 각각 증거 4칸을 채운다다음 장의 양식대로 실행 명령 · 출력 · 판정 · /context 사용률. 사용률은 /context를 한 번 쳐서 첫 줄의 숫자를 옮겨 적는다.

정답 diff는 git diff main..fix/defect-2 로 봅니다. 막히면 after-b2 브랜치로 갈아타면 3교시 출발선이 됩니다.

npm test

판정

통과 — 실패 확인 → 수정 → 통과

/context 사용률

/context 첫 줄의 % 를 그대로

에러 갤러리

막히는 지점 셋

01

테스트가 처음부터 통과한다

테스트와 함께 함수까지 고친 것. "src는 두고 테스트만 써서 실패 출력을 먼저 보여라"로 되돌린다.

02

기대값을 바꿔 통과시켰다

테스트 diff를 본다. "기대값은 고정, src/lib만 고치고 diff를 보여라"로 되돌린다.

03

스크린샷이 안 붙는다

맥은 Cmd+V로 이미지가 안 붙는다. Ctrl+V로 붙이고, 캡처는 Ctrl+Cmd+Shift+4.

💡팁 — 에러는 외우지 않습니다. 메시지를 그대로 Claude에 붙여넣어 고칩니다.
