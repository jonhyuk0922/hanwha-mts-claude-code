Token Economy and Session Control

Module 01 · Objectives

이 모듈에서 손에 남는 것

세션이 왜 무거워지는지 숫자로 보고, 끊고 줄이고 맡기는 세 동작을 몸에 붙입니다.

이 모듈에서 배울 것

  • /context로 세션이 무엇으로 차 있는지 층별로 읽고, 먼저 줄일 층을 고릅니다.
  • 무관한 작업은 /clear, 이어지는 작업은 범위를 지정한 /compact, 곁가지 질문은 /btw로 가릅니다.
  • 조사는 rg·ast-grep·서브에이전트에 맡기고, /usage로 오늘의 기준선을 숫자로 적습니다.

Why This First

편차는 도구가 아니라 세션 운영에서 생긴다

같은 Claude Code를 쓰는데 결과가 갈리는 이유를 첫 시간에 못박습니다.

대부분의 베스트 프랙티스는 하나의 제약에서 나온다. 컨텍스트 윈도우는 빠르게 차고, 찰수록 성능이 떨어진다.

Anthropic, Claude Code Best Practices (code.claude.com/docs)
왜 이걸 하나

세션이 차면 앞서 준 지침을 잊고 실수가 늘어납니다. 무엇으로 차는지 읽을 수 있어야 끊을 때와 맡길 것을 정할 수 있고, 그 규율이 파일과 명령으로 고정되면 팀 전체가 같은 결과를 냅니다.

/context

세션은 무엇으로 차 있나 — 네 층으로 읽는다

막대 하나가 세션 전체입니다. 위 두 층이 무엇인지 읽으면 먼저 줄일 곳이 정해집니다.

assets/images/01-4-context-layers.png 잡탕 대본 ①~⑤를 돌린 직후 /context 실행 화면 전체. 사용률 55~65% 상태

📌메모 — 도구 실행 결과와 파일 읽기 중 어느 쪽이 위에 있는지가 첫 판단입니다. 위층부터 줄입니다.

강사 화면 (1/2)

잡탕 세션을 일부러 만든다

여섯 줄을 순서대로 치면 앞 화면의 막대가 나옵니다. 먼저 앞의 세 줄입니다.

①

통독 요청

CLAUDE.md·README·package.json을 읽어 달라고 합니다.

②

테스트 전량

npm test를 돌려 출력을 그대로 받습니다.

③

파일 전문 읽기

src/screens/chart/ 3파일을 전문으로 읽게 합니다.

왜 이걸 하나

세 줄 모두 흔한 요청입니다. 잘못된 사용이 아니라 평범한 오전 작업이 막대를 채운다는 것을 먼저 봅니다.

강사 화면 (2/2)

나머지 세 줄, 그리고 /context

화면을 본 뒤 각자 ①~⑤를 그대로 따라 칩니다. ⑥은 앞 장의 막대를 다시 읽습니다.

④

곁가지 질문 2개

커밋 메시지 규칙과 브랜치 네이밍을 묻습니다.

⑤

로그 붙여넣기

docs/sample.log tail 800줄을 붙여넣습니다.

⑥

/context

막대를 읽고 위 두 층이 무엇인지 말합니다.

⚠️확인 — ⑤까지 마친 뒤 /context 사용률이 50%를 넘는지 봅니다. 못 미치면 ⑤의 줄 수를 늘립니다.

Three Cuts

/clear · /compact · /btw — 끊는 자리가 다르다

셋 다 컨텍스트를 줄이지만 남기는 것이 다릅니다. 표의 첫 행이 선택 기준입니다.

기준/clear/compact/btw
언제무관한 작업으로 넘어갈 때같은 작업을 이어갈 때흐름과 무관한 한 줄 질문
남는 것없음. 빈 세션에서 시작지정한 범위의 요약본 대화 그대로. 질문은 따로
이전 대화디스크에 남아 /resume 가능요약으로 대체건드리지 않음

이어갈 작업이면 범위를 적어 /compact, 아니면 /clear. 곁가지는 처음부터 /btw로.

즉시 따라하기 (1/5)

곁가지 질문을 /btw로 뺀다

①~⑤를 따라 친 뒤 /context를 찍고, 아래 한 줄을 그대로 입력합니다.

왜 이걸 하나

④에서 던진 곁가지 질문은 답을 받는 순간 본 대화에 남아 끝까지 따라다닙니다. 같은 질문을 /btw로 던지면 답은 받고 세션은 그대로입니다.

프롬프트 · /btw
/btw 이 레포의 브랜치 네이밍 규칙이 뭐야?
의미

본 대화를 건드리지 않고 한 줄 질문만 따로 묻고 답을 받습니다. 답은 세션에 쌓이지 않습니다.

본인 업무

구현 도중 "이 라이브러리 버전이 뭐지", "이 옵션 기본값이 뭐지" 같은 질문 전부.

바꿔 끼우는 자리

/btw 뒤 문장 전체. 예: "호가창 컴포넌트 props 타입이 뭐야?"

즉시 따라하기 (2/5)

범위를 적어서 /compact 한다

남길 것을 문장으로 적고, 끝나면 /context를 다시 찍어 막대를 비교합니다.

왜 이걸 하나

범위 없는 /compact는 남길 것을 Claude가 정합니다. 다음 작업에 필요한 것을 내가 적어 주면 요약이 작아지고 빠지는 것이 없습니다.

프롬프트 · /compact
/compact 호가 갱신과 관련된 파일 경로, 함수 이름, 지금까지 확인한 결론만 남겨라. 테스트 출력과 로그 본문은 버려라.
의미

지금까지의 대화를 요약으로 바꾸되, 남길 셋과 버릴 둘을 명시합니다.

본인 업무

긴 디버깅 끝에 수정으로 넘어갈 때. 원인과 위치만 남기고 시행착오는 버립니다.

바꿔 끼우는 자리

"호가 갱신" 자리에 지금 작업 이름. 예: "주문 폼 검증", "관심종목 정렬".

즉시 따라하기 (3/5)

읽지 말고 찾게 한다 — rg

폴더를 통째로 읽히는 대신 후보 파일과 줄 번호만 받습니다. 파일 본문이 세션에 안 들어옵니다.

왜 이걸 하나

파일 읽기 층은 Claude가 파일을 "열어서" 생깁니다. 검색 결과는 몇 줄이라 같은 조사를 해도 막대가 거의 안 움직입니다.

템플릿
파일을 열어 읽지 말고 rg로 [키워드]가 나오는 파일과 줄 번호만 목록으로 내라. 후보는 [N]개 이하로 좁혀라.
예시 프롬프트
파일을 열어 읽지 말고 rg로 applyQuote가 나오는 파일과 줄 번호만 목록으로 내라. 후보는 5개 이하로 좁혀라.

[키워드]에는 함수명이나 화면 이름을, [N]에는 다음 단계에서 열어 볼 수 있는 파일 수를 넣습니다.

즉시 따라하기 (4/5)

함수 단위로 뽑게 한다 — ast-grep

rg가 좁힌 후보 안에서 호출 패턴을 구문 트리로 찾아 파일:함수 목록만 받습니다.

왜 이걸 하나

문자열 검색은 주석과 변수명까지 잡습니다. 구문 단위로 찾으면 결과가 짧아지고, 그 짧은 결과가 그대로 답의 형식이 됩니다.

템플릿
후보 파일에서 ast-grep으로 [호출 패턴]을 찾아 파일:함수 단위로 뽑아라. 파일 본문은 출력하지 마라.
예시 프롬프트
후보 파일에서 ast-grep으로 applyQuote($$$) 호출을 찾아 파일:함수 단위로 뽑아라. 파일 본문은 출력하지 마라.

[호출 패턴]의 $$$는 인자 전체를 뜻하는 자리표시입니다. 함수명만 바꿔 끼웁니다.

즉시 따라하기 (5/5)

조사 자체를 서브에이전트에 맡긴다

읽는 일은 별도 컨텍스트에서 하고, 본 세션에는 요약 한 덩어리만 돌아옵니다.

왜 이걸 하나

서브에이전트는 자기 컨텍스트를 따로 갖습니다. 열어 본 파일이 아무리 많아도 본 세션 막대에는 결과 형식만큼만 더해집니다.

템플릿
서브에이전트를 써서 [조사 과제]를 조사하고, 결과는 [형식]으로만 돌려줘. 읽은 파일 본문은 이 대화에 올리지 마라.
예시 프롬프트
서브에이전트를 써서 호가 갱신 로직이 어느 파일 어느 함수에 걸려 있는지 조사하고, 결과는 파일:함수 목록으로만 돌려줘. 읽은 파일 본문은 이 대화에 올리지 마라.

[형식]을 "파일:함수 목록"처럼 짧게 못박을수록 돌아오는 양이 줄어듭니다. 마지막 문장은 빼지 않습니다.

자체 실습

같은 조사를 두 번 — A안과 B안

과제 문장은 하나로 고정합니다. 바뀌는 것은 조사 방법뿐이고, 재는 것은 사용률 차이뿐입니다.

A안 · 폴더 통독

문장 하나를 던지고 읽게 둔다

  • Claude가 관련 폴더의 파일을 열어 읽습니다
  • 읽은 본문이 전부 세션에 쌓입니다
→
B안 · rg → ast-grep → 서브에이전트

같은 문장을 세 프롬프트로 나눈다

  • 후보를 좁히고, 함수 단위로 뽑고, 요약만 받습니다
  • 세션에는 파일:함수 목록만 남습니다
왜 이걸 하나

방법이 다르면 답이 아니라 비용이 갈린다는 것을 내 화면의 숫자로 봅니다. 이 차이가 이 모듈의 판정선입니다.

자체 실습 · 과제

고정 조사 과제 한 문장

A안은 이 문장을 그대로 던지고, B안은 세 프롬프트의 빈칸에 이 과제를 넣습니다.

고정 조사 과제 · A안과 B안 공통
주문 수량 검증 로직이 어느 파일 어느 함수에 흩어져 있는지 파일:함수 목록으로 내라.
의미

답의 형식까지 문장에 넣습니다. 형식이 짧아야 두 안의 답을 나란히 비교할 수 있습니다.

본인 업무

"이 기능이 어디에 걸려 있나"를 묻는 조사 요청 전부. 수정 전에 늘 한 번은 하는 일입니다.

바꿔 끼우는 자리

"주문 수량 검증 로직" 자리에 조사할 기능. 예: "호가 갱신", "관심종목 정렬".

자체 실습 · 절차

A안 → /clear → B안, 그리고 숫자 다섯 칸

두 번 다 같은 출발선에서 시작하고, 끝날 때마다 /context 값을 적습니다.

  1. 01

    A안

    /clear 후 시작 사용률을 적고 과제 문장을 던집니다. 끝나면 A 종료 값을 적습니다.
  2. 02

    B안

    다시 /clear. 세 프롬프트의 빈칸을 수량 검증으로 바꿔 순서대로 던지고 B 종료 값을 적습니다.
  3. 03

    하락 %p

    A 종료에서 B 종료를 뺍니다. B 종료 /context 화면은 닫지 않습니다.

⚠️판정선 — A 종료 대비 B 종료 사용률이 15%p 이상 내려간 /context 화면을 보입니다.

자체 실습 · 결과

두 화면을 나란히 — 무엇이 줄었나

줄어든 것은 답이 아니라 파일 읽기 층입니다. 답의 파일:함수 목록은 두 안이 같아야 합니다.

assets/images/01-16-ab-context.png 강사 리허설의 A 종료·B 종료 /context 두 화면을 좌우로 붙인 캡처

⚠️확인 — B안의 파일:함수 목록이 A안과 다르면 판정 전에 어느 쪽이 빠뜨렸는지 먼저 봅니다.

/usage · 기준선

오늘의 기준선을 다섯 칸에 적는다

앞 네 칸은 방금 잰 값이고, 마지막 칸은 /usage가 보여 주는 오늘 누적입니다.

assets/images/01-17-usage-baseline.png B안 종료 직후 /usage 화면. 세션 한도와 주간 한도 두 막대가 보이는 상태
칸값
시작 사용률____ %
A 종료____ %
B 종료____ %
하락____ %p
/usage 오늘 누적____ %

이 다섯 칸은 마지막 모듈 지표 기록지와 같은 양식입니다.

세션 규칙 세 줄

/effort medium, 그리고 세션 중에 바꾸지 않는 것

토큰은 읽는 양만이 아니라 앞부분이 다시 계산될 때도 나갑니다. 이 모듈부터 지키는 세 줄입니다.

01

기본은 /effort medium

계획 모드와 리뷰 세션에서만 올립니다. 하루 종일 최상위로 켜 두는 습관을 여기서 끊습니다.

02

모델·MCP·CLAUDE.md는 세션 중 고정

셋 중 하나가 바뀌면 캐시가 깨져 앞부분을 통째로 다시 냅니다. effort를 바꿔도 같습니다.

03

바꿀 일은 /clear 뒤에

모델을 올리고 싶어지는 순간이 /clear 할 때입니다. 블록마다 자체 실습 시작도 /clear로 엽니다.

막히는 지점

여기서 멈추면 이렇게 푼다

증상을 보고 원인을 짚은 뒤 대응 한 줄을 그대로 씁니다.

01

"없는 명령입니다"

버전이 낮습니다. claude update 후 다시 엽니다. 안 되면 두 번째 탭의 새 세션이 /btw를 대신합니다.

02

/compact 뒤 필요한 게 사라짐

범위 없이 눌렀습니다. "빠진 [파일 경로]를 다시 읽어 결론만 남겨라"로 되살리고, 다음부터 범위를 적습니다.

03

B안이 15%p 안 떨어짐

/clear 없이 돌렸거나 파일 본문이 돌아왔습니다. /clear 후 재시도하고 마지막 문장을 확인합니다.

💡팁 — 에러는 외우지 않습니다. 메시지를 그대로 붙여넣어 고칩니다.
